A door for containers.
Not for the host.

A small Go gateway that turns public-key SSH into a narrow management interface for Incus. App users get shells inside containers they own. The host keeps its own door.

One authenticated path, then a hard stop.

The gateway parses a small command grammar and calls the local Incus CLI with fixed arguments. It never exposes the Incus socket, and it never opens a host shell for a client.

1
Public-key SSH to a private listener
The listener binds loopback or an address in Tailscale's IPv4 range, not the host's administrative port.
2
Username and key must both match
The project comes from server configuration, not from the client.
3
Parsed command, fixed backend arguments
Clients cannot choose images, profiles, projects, mounts or raw Incus flags.
4
Ownership check, then container execution
Every operation verifies the project and the app's owner label.
Host SSH stays where it is. Administrative access, Tailscale configuration and the Incus socket remain separate from the tenant-facing listener.

A shell that knows what it is

Connecting with no command opens a management prompt. ssh NAME starts incus exec against a container you own and wires the terminal through. There is no second network hop and no host shell in between.

Limits live in two places

The project restricts what a container may do. The application enforces ownership, name rules and per-container resource maxima. Neither relies on the client behaving well.

Unsupported is a real answer

pause, SFTP, previews, Docker and OpenTunnel-style exposure are not quietly approximated. They are outside the gateway and fail rather than pretend. pause cannot be done honestly with Incus containers; freeze keeps RAM and stop loses process state. The v0.3.0 image catalog only lists predefined, operator-cached native Linux images; it is not an OCI registry and does not add a Docker daemon, nesting, KVM or real virtual machines.

A small command set. No hidden verbs.

Management flags use = for values. Everything after ssh NAME belongs to the guest.

help

Show the supported subset.? and help all also work.

whoami

Return the authenticated app user and project.Useful as a first connectivity test.

new

Launch and start an owned container.Fruit name by default; --name=, --image=, --cpu=, --memory=, --processes=, --disk=.

ls

List only containers you own.-l adds known limits; accepts one name or glob.

image list

See operator-cached container images.Read-only; clients cannot pull, copy or delete images.

ssh

Open a guest shell or run one remote command.Streams stdin, stderr and the guest exit status.

start

Start a stopped container.resume is an alias. Process state is gone.

stop

Gracefully stop a container.Files persist; running processes do not.

restart

Gracefully restart a container.Same data, fresh processes.

rm

Permanently delete named containers.Deletes the root filesystem, even while running.

rm is destruction. It force-deletes the named container and its filesystem. Use it only for containers you created and confirmed disposable.

The boundary is the product.

This is infrastructure for trusted development work. It is not a hostile-tenant sandbox or a virtual machine.

What the gateway enforces

  • Public-key authentication bound to the requested app username
  • No passwords, anonymous auth or automatic account creation
  • Fixed project and profile; image choice limited to predefined native images the operator cached
  • Owner-label checks on list, exec and lifecycle operations
  • CPU, memory and process limits per container
  • Session channels only; agent, X11, environment and TCP forwarding refused
  • Strict host-key checking in the optional Go client

What you still have to do

  • Provision the restricted Incus project and profile
  • Cache predefined native images for approved image selection
  • Treat incus-for-devs incus as local host-root administration, never an SSH client command
  • Block guest access to host, private-network and cloud metadata endpoints
  • Protect the Incus socket: its access is effectively host-root authority
  • Provide disk quotas if the storage backend supports them
  • Size the host for committed RAM; swap is not part of the policy
  • Keep backups; persistence is not a backup strategy

From source to a shell.

The repository ships templates and a build procedure, not a universal installer. Build on Linux first, then prepare Incus and install the service.

Build on Linux

Build and test somewhere approved for compilation, not the target host. Keep the Linux binary; do not overwrite it with a cross-compiled client.

go mod verify
go test -race ./...
go vet ./...
go build -trimpath -o bin/incus-for-devs ./cmd/incus-for-devs

Prepare Incus

Provide the storage pool, managed bridge and a predefined cached image. Copy the build output and templates to the host, then run setup from that checkout. Setup checks them and, with --apply, creates missing project and profile resources; its default is a plan, and apply requires root.

./bin/incus-for-devs setup --templates deploy
sudo ./bin/incus-for-devs setup --templates deploy --apply

The default image is the cached alias ifd-ubuntu-24-04. --image accepts a local alias, an optional local: prefix or a 64-character fingerprint; remote references are rejected and nothing is downloaded. The default setup plan checks the daemon, pool, bridge and image, not the templates. Apply validates strict typed YAML, creates only missing resources, and fails on a mismatch instead of overwriting. OVN networks are not supported. In v0.3.0, other operator-cached native images become selectable with new --image. The separate setup --install-incus stage installs a fixed four-package dependency set for a fresh host; its plan, no-op gate and side effects are documented in Install the Incus dependency.

Configure and generate a host key

Install the Linux binary on the host. Use a dedicated nologin service account, and replace every placeholder in the example configuration.

useradd --system --user-group \
  --home-dir /var/lib/incus-for-devs \
  --shell /usr/sbin/nologin incus-for-devs
install -d -o incus-for-devs -g incus-for-devs -m 0700 /var/lib/incus-for-devs
install -d -o root -g incus-for-devs -m 0750 /etc/incus-for-devs
install -o root -g root -m 0755 bin/incus-for-devs /usr/local/bin/incus-for-devs
install -o root -g incus-for-devs -m 0640 prepared-config.json \
  /etc/incus-for-devs/config.json

runuser -u incus-for-devs -- /usr/local/bin/incus-for-devs keygen \
  --path /var/lib/incus-for-devs/host.key

install -o root -g root -m 0644 deploy/incus-for-devs.service \
  /etc/systemd/system/incus-for-devs.service
systemctl daemon-reload
systemctl enable --now incus-for-devs.service

Verify with a disposable container

Verify the host-key fingerprint, log in, create one container you can lose, run a command, then remove it.

ssh -p 2222 you@GATEWAY help
ssh -p 2222 you@GATEWAY new --name=operator-check
ssh -p 2222 you@GATEWAY ssh operator-check 'uname -a'
ssh -p 2222 you@GATEWAY stop operator-check
ssh -p 2222 you@GATEWAY start operator-check
ssh -p 2222 you@GATEWAY rm operator-check

Settings that matter

The listener must be loopback or an address in Tailscale's range on a nonprivileged port. Range checks are not proof of tailnet membership. The configuration file must not be writable by group or others. The host key must be a private regular file and must survive restarts, or every client will see a changed-host warning.

config.example.json is a shape to copy. It points at loopback, uses a placeholder key and the cached image alias, and sets operator maxima of 2 CPU, 4GiB memory and 512 processes. It will not work unedited.

Start narrow. New containers default to 1 CPU, 2GiB and 256 processes. Users can ask for more up to the operator's maxima when the host has room, so set those maxima deliberately.

Memory admission keeps a 1GiB reserve, subtracts memory already committed to the project and refuses a create or stopped-instance start when it does not fit. Active restarts do not charge resident memory twice. Start and restart also revalidate the stored limits against current maxima. CPU maxima are per-container caps, not a scheduler. Swap is not configured, counted or promised: size the host for RAM.

Honest gaps.

These are not roadmap promises. They are the parts of the experience the gateway does not provide.

CapabilityStatus
pause and RAM checkpointNot implemented. Incus freeze (operator-only) keeps RAM; stop loses process state.
SFTP, SCP, rsyncNo file-transfer endpoint. Subsystem requests are rejected.
Web previews and sharingNot implemented.
Docker and nested containersNot supported. Nesting is blocked by the project and profile.
OpenTunnel-style exposureNot implemented. No public per-container tunnel.
Direct per-container hostnamesNot implemented. Use the gateway's ssh NAME.
Multiple app usersConfiguration admits exactly one user.
Disk quotasDepends on the storage backend. A directory pool may not enforce one.
Host reboot recoveryNot verified. Guest autostart is disabled.
VM-grade isolationNot provided. Containers share the host kernel.
Arbitrary OCI, Windows, real VMsNot supported. v0.3.0 selects only predefined, operator-cached native Incus container images. No Docker or OCI daemon, nesting or KVM/real-VM path.
