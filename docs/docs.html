v0.3.0. Incus 6.0.0 on Ubuntu 24.04. Go 1.26+.

Version 0.3.0. Source and release notes are on GitHub; build from source with Go 1.26+. Linux amd64 and macOS arm64 cross-builds were verified. The CLI binary and systemd service are named incus-for-devs.

Overview

incus.ssh is one Go executable with two modes. Server mode runs a private SSH listener beside Incus. Client mode invokes your installed OpenSSH with strict checking and no forwarding. Plain ssh works without the client.

The server maps a configured app username and public key to a fixed Incus project. It parses a small management grammar into fixed argument vectors and runs incus over the local socket. A guest command executes through /bin/sh -lc inside a container the user owns. No host shell is involved.

The gateway supports create, list, shell, start, stop, restart and remove. resume is an alias of start. New containers default to 1 CPU, 2GiB memory and 256 processes; the operator's values are per-container maxima. Names are fruit-based unless you pass --name=.

The v0.3.0 release adds a read-only catalog of predefined native images cached by the operator and new --image=REF to choose among them. The configured image remains the default, and the client still cannot pull or copy an image.

Requirements

  • Linux host with Incus installed and initialised
  • A storage pool and a managed bridge network matching the templates, or edited templates (OVN is not supported)
  • A predefined, approved native Incus Linux image cached locally, plus any additional images the operator caches for image selection
  • Root access for installation and project preparation
  • Go 1.26 or newer to build
  • OpenSSH on client machines; the compiled client is optional

The shipped profile expects a pool named devpool and a bridge named incusbr0. incusbr0 is also fixed in the project's restricted.networks.access. If you use different names, update the project and profile together. The setup command checks these; it does not create the pool or network.

Guest network policy is operator work. The repository does not install a firewall. Block guest access to host services, private networks and cloud metadata endpoints, and allow only the DNS and egress the containers need. Test the rules before handing out shells.

Build and test

Build and test on an approved Linux development host, not on the target host.

git clone https://github.com/4nkitd/incus.ssh.git
cd incus.ssh

go mod verify
go test ./...
go test -race ./...
go vet ./...
go build -trimpath -o bin/incus-for-devs ./cmd/incus-for-devs

A client binary for another platform is optional and must use a different output name. The server itself runs on Linux; the Darwin build is a client only. Windows builds are not supported. Do not write the Darwin build to bin/incus-for-devs or replace the Linux binary on the host with it. 

# optional client-only build; note the distinct output name
GOOS=darwin GOARCH=arm64 CGO_ENABLED=0 \
  go build -trimpath -o bin/incus-for-devs-darwin-arm64 ./cmd/incus-for-devs

Unit and SSH integration tests use temporary keys and a fake backend. They do not need Incus. Real lifecycle testing needs a dedicated project and disposable container names.

Prepare Incus

Create a dedicated project and fixed profile. The example restricts privilege, nesting, low-level configuration, host disk devices and proxy devices. Containers default to one CPU, 2 GiB and 256 processes, with operator maxima of two CPUs, 4 GiB and 512 processes. 

incus project create ifd-dev
incus project edit ifd-dev < deploy/project.yaml
incus --project ifd-dev profile create ifd
incus --project ifd-dev profile edit ifd < deploy/profile.yaml

# cache an image and use its local alias in the configuration
incus image copy images:ubuntu/24.04 local: --alias ifd-ubuntu-24-04

incus project show ifd-dev
incus --project ifd-dev profile show ifd

Do not enable limits.memory.swap while the project blocks low-level configuration; Incus 6 classifies it as a low-level option and rejects the launch. The profile intentionally omits it.

Prepare the existing runtime (default mode)

After building on Linux, setup performs project and profile preparation against an existing daemon. This default mode starts as a plan: it checks the daemon, pool, bridge and cached image, and changes nothing. --apply is explicit, requires root, and is the only default-mode run that creates project and profile resources. 

./bin/incus-for-devs setup --templates deploy
sudo ./bin/incus-for-devs setup --templates deploy --apply \
  --project ifd-dev --profile ifd \
  --pool devpool --network incusbr0

Run setup from an extracted Linux archive containing bin/incus-for-devs and deploy/, keeping the standard release layout, or from a source checkout after building. An installed binary still needs --templates pointing at the deployment templates.

FlagMeaning
--templates DIRDirectory with project.yaml and profile.yaml. Defaults to deploy; any other value must be an absolute path.
--applyMode-dependent. In the default runtime mode, create missing project and profile resources; without it, setup only prints a plan. With --install-incus, update APT lists, run a bounded simulation, then install or upgrade the fixed dependencies under --no-remove. Both uses require root.
--project, --profileNames to prepare. Defaults are ifd-dev and ifd. Each is a lowercase slug of at most 48 characters; default is rejected.
--pool, --networkExisting storage pool and managed bridge the templates must reference exactly. Defaults are devpool and incusbr0. Only bridge networks are accepted; OVN is rejected.
--imageA cached local alias, an alias with a local: prefix, or a 64-character fingerprint. Defaults to ifd-ubuntu-24-04. Remote references such as images:ubuntu/24.04 are rejected.
--config FILERead only the image field from a gateway JSON config. It overrides --image.
--incusAbsolute path to the Incus CLI. Defaults to /usr/bin/incus. Root runs require a trusted, root-owned executable and directories that are not writable by group or others.
--install-incusSeparate dependency-only stage for a fresh host. It requests four packages plus required distribution dependencies and does not initialise Incus or prepare the runtime. See Install the Incus dependency.

The default setup plan verifies that the Incus daemon is reachable and trusted, the pool and network exist, the network is a managed bridge, and the image alias or fingerprint resolves to a cached container image. It does not parse the templates, so template problems are reported only at apply. The account running setup needs access to the local Incus socket; apply requires root.

Apply validates the templates as strict typed YAML: only known top-level keys are accepted, duplicate keys, aliases and multiple documents are rejected, and config values must be non-null scalars. Template and config files must be regular, non-symlink files not writable by group or others. The project must set the required restricted and container-only settings, including features.storage.volumes=true, features.storage.buckets=false and exactly one allowed managed bridge. The shipped template also includes container-only resource limits. The profile must set the fixed security values and define exactly one root disk and one managed NIC.

Existing project and profile resources that match exactly are left unchanged. Any mismatch fails with a difference report and is never overwritten or deleted. Apply creates only missing resources; if a later create fails after an earlier one succeeded, setup reports the partial state and asks you to re-run to reconcile. It verifies the result after creating. This runtime mode never installs packages, writes systemd or SSH configuration, creates pools or networks, downloads images, or changes anything outside the configured project and profile.

The pool, bridge and local image must already exist. Use the manual commands above if you prefer to manage project and profile edits yourself.

Install the Incus dependency

--install-incus is a dependency-only stage for a fresh host. Without --apply it is a plan: it reads the OS release and file metadata, runs no commands, changes nothing, and reports the recognized distribution and planned steps. It cannot check APT candidates or daemon readiness. When packages are needed, an unrecognized distribution fails as unsupported; a recognized one with no candidate fails during apply. Existing complete installations can use the read-only verification path on other distributions. Combining it with any other preparation flag is rejected. Use it before runtime preparation when Incus is absent, then run the default setup separately. 

./bin/incus-for-devs setup --install-incus
sudo ./bin/incus-for-devs setup --install-incus --apply

With root --apply it updates APT lists first, then runs a bounded simulation with --no-remove before installing packages. --no-remove is the primary removal guard and blocks package removals. It installs or upgrades the fixed set below plus required dependencies, and does not perform a full system upgrade. It does not run incus admin init, initialise storage or networking, prepare a project or profile, configure a public listener, pool or SSH, start the gateway, or add third-party repositories, snap or LXC packages:

  • incus, incus-client: daemon and CLI
  • ca-certificates: CA trust roots for HTTPS image copies
  • dnsmasq-base: DHCP/DNS helper required by a managed bridge

Apply skips APT only when the trusted client and daemon binaries exist and the daemon's /1.0 metadata is reachable. Package presence alone is not the test; a missing helper such as dnsmasq-base is not detected or repaired on such a host. If the daemon is stopped or unreachable, apply fails without APT; start or repair it, then retry.

Package maintainer scripts can start Incus units, restart dnsmasq, and change subuid/subgid or sysctl files, so schedule a root maintenance window. Installation is not daemon or service readiness, and the installer does not start the gateway service; start and verify the daemon separately. The package environment ignores http_proxy, https_proxy and APT_CONFIG; configure an APT proxy in apt.conf.d.

Images

The v0.3.0 image catalog is read-only and local. It lists predefined native Incus Linux images already cached in the configured project; it is not a registry client and never contacts an image server. The operator decides what is cached and approved, and the client may only choose from that set. 

ssh -p 2222 you@GATEWAY image list
ssh -p 2222 you@GATEWAY image list --json

Text output has one image per line: the preferred alias or a short fingerprint, a 12-character fingerprint prefix, and the OS release. JSON returns {"images":[...]} with the full fingerprint, sorted aliases and optional description, os, release and architecture. VM images and metadata without a valid fingerprint are omitted.

new --image=REF selects one of those cached images for a new container. REF is an alias shown by image list or a 64-character fingerprint, optionally prefixed with local:. Explicit selections reject remote references such as images:debian/12, URLs, control characters and path traversal. Without the flag, the operator's configured image is used unchanged; a remote default may download an image. Configure a cached local default for offline creation. An alias may contain a slash only when the cached image metadata defines that exact alias, for example debian/12.

The backend resolves the reference inside the cached catalog and passes only the immutable image fingerprint to incus launch. Changing an alias later does not change an existing container, and ls --json reports the pinned fingerprint recorded by Incus rather than a mutable alias. Unknown aliases, aliases matching more than one cached image and non-container images fail before creation. ls -l keeps its six text columns; the image is a JSON-only field.

Caching images is operator work

The image cache is an approval boundary owned by root and the operator. Clients have no command to pull, copy, import, alias or delete an image, and the gateway uses no registry credentials. Cache images locally through the operator mode, which forwards to native Incus with full administrator authority: 

incus-for-devs incus --help
sudo incus-for-devs incus -- image copy images:debian/12 local: --alias debian-12
sudo incus-for-devs incus -- image list local:

The restricted project and fixed profile apply to every cached image, along with unprivileged execution, the namespace root mapping and the CPU, memory, process and disk limits. The image itself is still a native Incus container image. The lifecycle is persistent in the container sense: the root filesystem survives stop and start, while running processes do not. Prefer images that include /bin/sh, because guest commands run through /bin/sh -lc.

A VM-like workflow, one container at a time

With limits.max_instances set to 1, list the cache, choose a Debian image, then keep one container as a long-lived development environment: 

ssh -p 2222 you@GATEWAY image list
ssh -p 2222 you@GATEWAY new --image=debian-12 --name=dev
ssh -t -p 2222 you@GATEWAY ssh dev
# inside: install packages and keep files across stop and start

This gives a VM-like persistent development shell, but it is not a VM. Containers share the host kernel; there is no hardware virtualisation, no Docker or OCI daemon, no nesting, and no KVM or real-VM path. A minimal image without /bin/sh can be created, but its shell commands fail; fix that by caching a different image as the operator, not by granting more privilege. Arbitrary OCI images, Windows images and real virtual machines are not supported on any host.

Local operator mode

incus-for-devs incus is a local application mode for host administration, not an SSH management command. incus-for-devs incus --help prints its usage and exits 0 without root. sudo incus-for-devs incus -- ARGS runs the native Incus CLI locally with the operator's full administrator authority.

The configured project is the native CLI's default. Native --project NAME overrides it. Clear it for global commands that reject a project: 

sudo incus-for-devs incus -- --project= query /1.0
sudo incus-for-devs incus -- --project= list --all-projects

This mode is deliberately unrestricted: it is not a sandbox, it is not exposed through the SSH listener, and no client or guest can invoke it. Treat every invocation as host-root administration. Use it to cache approved images and perform deliberate host work, not to give a client a general Incus shell.

Configure

Start from config.example.json. It is a template, not a working deployment. Replace the placeholder key, set the image to the cached alias used by setup (for example local:ifd-ubuntu-24-04), choose a listener, and point the host key at the path you will generate. The example's 127.0.0.1 listener is reachable only on the host; for a remote client, bind the gateway's tailnet address instead. 

{
  "listen": "127.0.0.1:2222",
  "host_key": "/var/lib/incus-for-devs/host.key",
  "incus_binary": "/usr/bin/incus",
  "image": "local:ifd-ubuntu-24-04",
  "profile": "ifd",
  "operation_timeout_seconds": 120,
  "max_sessions": 8,
  "limits": {
    "max_instances": 1,
    "cpu": 2,
    "memory": "4GiB",
    "processes": 512
  },
  "users": [
    {
      "name": "you",
      "project": "ifd-dev",
      "authorized_keys": ["ssh-ed25519 AAAA... you@example"]
    }
  ]
}
FieldMeaning
listenLoopback, a Tailscale IPv6 address, or an IPv4 address in 100.64.0.0/10; port 1024-65535. This is a range check, not proof of tailnet membership. Wildcard and public binds are rejected.
host_keyAbsolute path to the persistent SSH host key.
incus_binaryAbsolute path to the Incus CLI.
image, profileThe default cached image and the fixed profile. The profile cannot be overridden. In v0.3.0, new --image may select another cached image; an uncached reference is rejected. Keep this value as the cached local alias checked by setup.
limitsPer-container maxima for CPU, memory and processes. The defaults a client gets when it requests nothing are 1 CPU, 2GiB and 256 processes. max_instances counts instances in the project.
usersExactly one app user: name, project and 1-16 public keys.

Configuration must be a regular file not writable by group or others. Keys must be ordinary single-line public keys; authorized-key options, certificates and duplicate keys are rejected. Omit limits.disk when the storage backend cannot enforce a quota; explicit --disk requests then fail.

Install the service account and host key

useradd --system --user-group \
  --home-dir /var/lib/incus-for-devs \
  --shell /usr/sbin/nologin incus-for-devs

install -d -o incus-for-devs -g incus-for-devs -m 0700 /var/lib/incus-for-devs
install -d -o root -g incus-for-devs -m 0750 /etc/incus-for-devs
install -o root -g root -m 0755 bin/incus-for-devs /usr/local/bin/incus-for-devs
install -o root -g incus-for-devs -m 0640 prepared-config.json /etc/incus-for-devs/config.json

runuser -u incus-for-devs -- /usr/local/bin/incus-for-devs keygen \
  --path /var/lib/incus-for-devs/host.key

keygen creates a new Ed25519 key with mode 0600 and refuses to overwrite an existing file. Keep it across upgrades. Losing it changes the fingerprint clients trust.

Run as a service

The repository includes a systemd unit. It runs a nologin account and grants incus-admin only as a supplementary group to the service process. 

install -o root -g root -m 0644 deploy/incus-for-devs.service \
  /etc/systemd/system/incus-for-devs.service
systemctl daemon-reload
systemctl enable --now incus-for-devs.service
systemctl status incus-for-devs.service --no-pager

A service that is “active” and a listening socket prove very little. Complete the first-login checks below before treating the deployment as working.

First login

Obtain the gateway's host-key fingerprint through trusted administrative access. Compare it with what the listener presents, then pin it. Do not skip this because the listener is on a private network. 

ssh -p 2222 you@GATEWAY help
ssh -p 2222 you@GATEWAY whoami --json
ssh -p 2222 you@GATEWAY new --name=operator-check --cpu=1 --memory=2GiB
ssh -p 2222 you@GATEWAY ssh operator-check 'uname -a'
ssh -t -p 2222 you@GATEWAY ssh operator-check
ssh -p 2222 you@GATEWAY stop operator-check
ssh -p 2222 you@GATEWAY start operator-check

When operator-check is confirmed disposable:

ssh -p 2222 you@GATEWAY rm operator-check
Removal is permanent. rm force-deletes the container and its root filesystem. It is not a pause and it cannot be undone from the gateway.

Value flags require =: --cpu=1 works, --cpu 1 does not. --json is a bare flag. Names use 1-63 lowercase letters, digits or hyphens, start with a letter and end with a letter or digit. Sizes need a positive integer and a unit such as 512MiB or 2GB. Image references are ASCII, at most 256 bytes, and name a cached alias or 64-character fingerprint; local: is the only accepted prefix. Unknown and duplicate flags fail.

Without --name=, new picks a fruit name such as mango. Bare fruit names are used first. Only when every bare name is taken does it fall back to suffixed names such as kiwi-2, using the lowest free suffix from 2 to 100 for each fruit. A name supplied with --name= is used exactly as given and fails if it already exists.

New containers default to 1 CPU, 2GiB memory and 256 processes. A request may go up to the operator's maxima. Memory is admitted only if the host has room after a 1GiB reserve and after counting memory already committed to the project; the check fails closed if host memory cannot be read. Starting a stopped instance requires fresh admission. Restarting a running instance revalidates operator ceilings without charging its resident memory again. Lowered ceilings can prevent an instance from starting or restarting. CPU maxima are per-container caps, not a scheduler: the gateway does not balance or reserve CPU time. The host policy is about RAM, not swap; swap is not configured, counted or promised.

After ssh NAME, everything belongs to the guest, including --json. The guest command runs through /bin/sh -lc. Quote the complete command locally when it contains pipes, variables or spaces.

JSON output

The management prompt supports Up/Down history, backspace and Ctrl-L to clear and redraw the current line. History is limited to 100 entries in the current SSH session and is never written to disk. Guest shells receive their own key streams unchanged.

Interactive prompts and help use cyan, running status uses green, stopped status uses amber and plain-text errors use red. JSON, non-PTY output and guest program output are not decorated. Colors are disabled for an empty or dumb terminal, or a nonempty NO_COLOR in the server process.

Optional Go client

Client mode replaces itself with OpenSSH. It forces strict host-key checking, disables agent forwarding and clears forwardings. It uses your SSH configuration and agent. Client options come before the management command. 

./bin/incus-for-devs --target you@GATEWAY --port 2222 help
./bin/incus-for-devs --target you@GATEWAY --port 2222 ls --json
./bin/incus-for-devs --target you@GATEWAY --port 2222 ssh demo
./bin/incus-for-devs --target you@GATEWAY --port 2222 ssh demo 'printf "%s\n" "hello world"'

INCUS_FOR_DEVS_TARGET=your-ssh-alias ./bin/incus-for-devs ls --json

With one argument after ssh NAME, the client sends it as the complete guest command. With several arguments, it quotes each one. Omitting --port leaves the port to OpenSSH configuration; there is no implicit 2222.

Security model

The gateway is a single trusted-user service for unprivileged development containers. It is not a multiuser service, a hostile-tenant sandbox, or a VM isolation boundary.

  • Authentication requires both the configured username and a registered public key. Tailscale provides transport, not app identity.
  • The listener accepts loopback, Tailscale's IPv6 prefix, or IPv4 addresses in 100.64.0.0/10, on ports 1024-65535. That checks the address range, not tailnet membership or ACLs.
  • The service's Incus socket access is effectively host-root authority. The nologin account and systemd sandbox restrict how it is reached, not what it can do.
  • Containers are unprivileged with an isolated UID map, no nesting, no arbitrary host disk or path mounts and no proxy devices. They share the host kernel, whichever cached image is selected.
  • Clients cannot choose a project, profile, host mount or raw Incus flag. --image may only select an image already cached by the operator, and the resolved fingerprint, not the client string, reaches Incus.
  • The image cache is an operator approval boundary. Clients cannot pull, copy, import, alias or delete images, and the gateway has no registry credentials or image mutation command.
  • incus-for-devs incus is a local operator mode with full administrator authority, not an SSH management command. It is never exposed to clients or guests.
  • Every list, shell and lifecycle request checks the container's owner label and project.
  • Only SSH session channels are accepted. Agent, X11, environment, TCP forwarding and subsystem requests are refused.
  • CPU and memory maxima are resource limits, not scheduling guarantees. Creation and starting stopped instances check host memory. An active restart revalidates limits without charging resident memory twice. Admission is not a reservation.
  • Swap is outside the host policy: the gateway does not configure it, count it as capacity or promise it.
  • A directory storage pool may not enforce a disk quota. CPU and memory caps do not stop a full disk.
  • Persistence across a graceful stop and start is not a backup. Host reboot recovery is not verified.

The default runtime mode of setup prepares the restricted project and fixed profile only when run with root and --apply. It creates missing resources, never edits or deletes existing ones, and verifies the result. In this mode it does not write SSH, firewall, systemd or network configuration, create pools or networks, or download images. The --install-incus path is separate host maintenance. See Install the Incus dependency for its fixed package set, no-op gate and side effects. Verify daemon readiness separately. Never expose the Incus socket or incus-admin group to a client or guest. The project restrictions depend on the operator keeping that boundary intact.

Use the distribution's documented Incus package path as the operator. Setup does not add third-party repositories, snap or LXC packages. The plan cannot determine this in advance because it runs no commands.
setup --install-incus reports an unsupported distributionThis is not the same as a missing package candidate. The OS release is not recognized, so apply is not attempted. Install Incus through the distribution's documented path.
setup --install-incus --apply fails without invoking APTApply checks both trusted Incus client and daemon binary paths and the daemon's /1.0 metadata before APT. A stopped or unreachable daemon fails closed with no package change. Start or repair the daemon, then retry.
All four packages are installed but apply is not a no-opThe no-op test is not dpkg package presence. Both trusted binary paths must exist and the daemon's /1.0 metadata must be reachable. A missing helper such as dnsmasq-base is also not repaired on an existing complete host.
An APT proxy set in the environment is ignoredThe package environment is fixed and minimal: http_proxy, https_proxy and APT_CONFIG are not read. Configure an APT proxy through apt.conf.d instead.
Native image copy fails HTTPS or certificate verificationA fresh minimal VM may lack CA trust roots. The installer's fixed dependency set includes ca-certificates; confirm it is installed and the host trust store is populated before operator image caching. On an existing complete host, a missing CA root does not by itself trigger a repair.
The installer finished but the Incus daemon is unreachable or not readyA successful dependency install is not daemon readiness. If service startup is policy-blocked or the daemon is not running, start and verify it separately. The installer does not initialise storage or networking. Verify daemon presence and readiness with operator Incus access before running the default setup.
--install-incus cannot be combined with ...The installer is a separate dependency stage. Run it alone with at most --apply, then run the default setup to prepare the existing project and profile.
incus-for-devs incus refuses an operationincus-for-devs incus --help works without root. Actual Incus operations need root and are local-only; this mode is never available over the SSH management port.
setup V1 requires a managed bridge networkOVN is not supported. Point --network at a managed bridge and keep the template in sync.
Native bridge fails because dnsmasq is missingThe managed bridge needs the dnsmasq-base executable. It is in the installer's fixed set, but a complete host that skips APT is not scanned for it; install it deliberately.
--apply requires rootRun setup with the privileges needed to create the project and profile, or run it without --apply for a plan.
pause is unsupportedExpected. Stop the container or use operator-only Incus freeze; neither restores RAM state to disk.
client mode requires OpenSSH on PATHInstall OpenSSH or use stock ssh directly.
Guest output is truncatedOlder builds could lose output on a blocked stream. Use a current build; the session now aborts instead of reporting false success.

Development

Package responsibilities: internal/gateway handles SSH authentication and sessions, internal/command parses and dispatches the management grammar, internal/incus enforces ownership, admission and fixed CLI arguments, internal/names generates fruit names, internal/setup prepares Incus, and internal/app loads configuration and starts the server.

Run gofmt, tests, the race detector and go vet before opening a pull request. Update CHANGELOG.md for behavior changes, and keep the site in docs/ in sync with the README. Read CONTRIBUTING.md and SECURITY.md. Security reports should not be public issues.
